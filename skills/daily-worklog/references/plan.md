# 自动化工作日志填报系统 — 方案 B 详细设计

## Context

用户为软件外包公司 QA，每日需向公司内部系统（https://prj.chinasoftinc.com/prj/index.jsp#）填报工作日志。已积累 3 个月历史报工数据（282 条，存储于 Excel）。希望通过 Agent 交互式流程，每日根据关键词自动匹配历史任务、生成日志、经用户确认后自动填入系统。

## 已确认的需求与约束

| 项目 | 详情 |
|------|------|
| 数据源 | 3 个 Excel 文件（3月126条、4月112条、5月44条），位于 `E:\Downloads` |
| 关键字段 | 工作项1/2/3、工作日志、项目名称、投入时间(H)、申报类型 |
| 每日输入 | 关键词列表（如"XX项目 需求评审 测试用例"） |
| 匹配策略 | 关键词多字段模糊匹配，多条结果自动聚合生成综合日志 |
| 目标系统 | https://prj.chinasoftinc.com/prj/index.jsp# |
| 浏览器 | RunningCheeseChrome（`D:\Program Files\RunningCheeseChrome\App\chrome.exe`） |
| 登录 | 用户提前手动登录，Agent 不处理登录 |
| 确认环节 | 生成日志后需用户确认 → 保存草稿后需用户确认 → 提交 |

## 已确认的设计决策

1. **Chrome 启动方式**：接受带 `--remote-debugging-port=9222` 启动，提供一键启动脚本
2. **工时策略**：聚合时取匹配记录的平均工时；若多条记录总工时超过 8 小时，按比例压缩至 8 小时以内
3. **匹配粒度**：关键词采用"包含即匹配"
4. **填报时机**：支持当日填报，也支持补填指定历史日期
5. **工作项映射**：历史 Excel 中的「工作项」字段与系统下拉选项一一对应，无需额外映射表
6. **已有记录处理**：检测到当天已有填报记录时，暂停流程并提示用户手动处理（不自动覆盖/追加）
7. **项目搜索**：使用 Excel 中的「项目名称」作为搜索关键词，支持模糊匹配

**初始化脚本功能**：

- 输出 `task_db.json` 到工作目录

#### 2. 匹配引擎

**算法**：多关键词模糊匹配

```python
def match_tasks(keywords: list[str], task_db: list[dict]) -> list[dict]:

    支持多关键词 OR 匹配（匹配任意一个即入选）
```

**匹配字段优先级**：
1. 工作项1/2/3（精确匹配权重高）
2. 工作日志（模糊匹配）
3. 项目名称（辅助匹配，支持模糊匹配）

**工作项映射说明**：
历史 Excel 中的「工作项」字段值与系统下拉选项为一一对应关系，匹配结果中的工作项值可直接用于 Playwright 填单时的下拉选择，无需额外映射表。

**输出**：匹配到的历史记录列表（0~N 条）

#### 3. 聚合引擎

**逻辑**：
- 按 `申报类型` + `项目名称` + `工作项1` 分组
- 同一组内合并 `工作日志`（去重后拼接，不超过500字）
- 工时取该组的**平均投入时间**，并向上取整到 **0.5 的倍数**
- 生成当日日志条目：
  - 申报类型（决定填到项目工时还是公共工时）
  - 项目/工作项/工时/日志内容

**工时计算规则**：

1. 每组取平均工时，向上取整到 **0.5 的倍数**
2. 计算所有分组的总工时；若总和超过 8 小时，**按比例压缩**各组工时，使总和恰好为 8 小时
3. 压缩后各组工时仍保持 0.5 的倍数

```python
def round_to_half(value: float) -> float:
    """将工时向上取整到0.5的倍数"""
    return math.ceil(value * 2) / 2

def compress_hours(items: list[dict]) -> list[dict]:
    """
    对聚合后的工时进行压缩
    1. 先按0.5取整
    2. 若总和>8，按比例压缩至8，再按0.5取整
    """
    for item in items:
        item["工时"] = round_to_half(item["工时"])
    total = sum(item["工时"] for item in items)
    if total > 8.0:
        factor = 8.0 / total
        for item in items:
            item["工时"] = round_to_half(item["工时"] * factor)
        # 二次压缩：若仍超过8，从最大项依次减0.5
        while sum(item["工时"] for item in items) > 8.0:
            max_item = max(items, key=lambda x: x["工时"])
            if max_item["工时"] >= 0.5:
                max_item["工时"] -= 0.5
    return items
```

#### 4. Playwright 浏览器自动化

**连接方式**：`connect_over_cdp` 连接用户已启动的 Chrome

**前提条件**：
- 用户需用以下参数启动 Chrome：
  ```
  chrome.exe --remote-debugging-port=9222
  ```
- 已登录目标系统

**填单流程**（基于截图分析）：
1. 连接 `http://localhost:9222`
2. **定位到日历页**（URL 含 `prj/index.jsp#`）
3. **检查目标日期状态**：
   - 若日期格子中已显示"申报Xh"等字样，说明当天已有填报记录
   - **暂停流程，截图提示用户"当天已有记录，请手动处理后重新发起"**（不自动覆盖/追加）
4. **点击目标日期**（日历网格中的数字；支持指定历史日期补填）
5. 进入填报详情页，遍历生成的日志条目：

   **项目工时填报（申报类型=项目报工）**：
   - 点击"+ 增加行"
   - 点击"项目"下拉框 → 输入项目名称（支持模糊匹配）→ 点击查询 → 等待表格加载 → 点击匹配行
   - 点击"工作项"下拉框 → 选择工作项（历史数据中的工作项值与系统选项一一对应，直接匹配）
   - 在"投入时间(H)"输入框填入工时
   - 在"详细日志"文本框填入日志内容

   **公共工时填报（申报类型=通用报工）**：
   - 点击"+ 增加行"
   - "部门"已固定为"电信与AIoT业务线"
   - 点击"工作项"下拉框 → 展开树形菜单 → 选择叶子节点工作项
   - 在"投入时间(H)"输入框填入工时
   - 在"详细日志"文本框填入日志内容

5. 点击"保存草稿"
6. 截图反馈结果

**元素定位策略**：
- 优先使用 CSS selector / XPath
- 关键操作前截图，失败后便于排查
- 预留手动介入接口（用户可随时接管浏览器）

### 错误处理

| 场景 | 处理策略 |
|------|----------|
| 无匹配记录 | 告知用户无匹配，请补充关键词或提供具体日志内容 |
| Chrome 未启动/未开启调试端口 | 提示用户启动命令，提供一键启动脚本 |
| 页面元素定位失败 | 截图当前页面，提示用户页面结构可能变更，需更新 selector |
| 保存草稿失败 | 截图报错信息，暂停流程等待用户介入 |
| 当天已有填报记录 | **暂停流程，截图提示用户手动处理**（不自动覆盖/追加） |
| 工时总和超过8H | **按比例自动压缩至8小时以内**，并在草稿展示时告知用户 |
| 工时不是0.5的倍数 | 自动向上取整到0.5倍数，并告知用户 |
| 日志超过500字 | 自动截断至500字以内，并告知用户 |

### 一、新增业务规则

| 编号 | 规则 | 实现位置 | 说明 |
|------|------|----------|------|
| R-01 | **叶子工作项聚合** | `engine.py:aggregate_tasks` | 聚合键从 `(申报类型, 项目名称, 工作项1)` 改为 `(申报类型, 项目名称, 工作项叶子)`，其中 `工作项叶子 = 工作项3 or 工作项2 or 工作项1`。避免同一 `工作项1` 下不同叶子节点被合并。 |
| R-02 | **总工时强制对齐 8H** | `engine.py:adjust_to_eight` | 无论原始总工时超过还是不足 8 小时，一律按比例调整（压缩或放大），并通过二次修正使总和严格等于 8.0H。 |
| R-03 | **项目关键词过滤公共工时** | `engine.py:is_project_specific_keyword` + `fill_worklog.py:905` | 若关键词在 `task_db.json` 的 `项目名称` 字段中出现过，则视为具体项目关键词，自动过滤匹配结果中的公共工时记录。 |
| R-04 | **日期业务规则过滤** | `engine.py:filter_by_date_rules` + `fill_worklog.py:917` | 361评估：仅允许周五或节假日前一天填报；审计（流程遵从度审计）：仅允许每月 20 日及以后填报；排产：仅允许每月 1-10 日（上旬）填报。 |
| R-05 | **月份关联性替换** | `engine.py:replace_month_in_logs` + `fill_worklog.py:925` | 日志中若出现非当前月/上月的 `X月`/`X月份` 表述，自动替换为当前月数字（如"3月复盘"→"5月复盘"），保留记录而非过滤。 |
| R-06 | **脚本永不自动提交** | `fill_worklog.py`（已移除 `--submit`） | 删除 `argparse` 的 `--submit` 参数及全部自动提交逻辑。保存草稿后终止，明确提示用户手动核对并点击提交。 |
| R-07 | **加载时自动清理无用字段** | `engine.py:load_task_db` | 加载 `task_db.json` 后，仅保留 9 个核心字段（申报类型、申报日期、项目名称、工作项1/2/3、投入时间(H)、工作日志、search_text），剔除审批状态、提交时间等系统生成字段。 |
| R-08 | **节假日列表配置** | `config.yaml:preferences.holidays` | 配置全年节假日日期（YYYY-MM-DD），用于 R-04 中"节假日前一天"的判断。 |

| R-42 | **降级补充显式标注** | `fill_worklog.py:_run_fill_impl` | `--preview` 输出中，来自非活跃项目的补充记录追加 `[历史库/非活跃]` 标注，确保用户知情。 |

### 四、工程方法约束（已写入 memory）

1. **先诊断后动手**：遇到页面交互问题，优先设计诊断脚本（JS 查询 DOM 结构）而非盲目试改。
2. **增量调试（单行先行）**：新增功能先测单行，验证通过后再扩展多行，避免多变量同时失效导致定位困难。

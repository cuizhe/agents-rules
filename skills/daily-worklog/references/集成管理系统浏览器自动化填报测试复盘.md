## 二、踩坑记录与分析

### 坑-1：草稿检测 false positive（删除后无法重新填报）

**现象**
- 用户在系统页面手动删除已有记录后，脚本仍报告"检测到已有填报记录"并终止。
- 重新检查页面状态：`hourInput=False`，无 combo 值，但脚本判断 `has_draft=True`。

**根因**
- `is_detail_page_has_draft` 函数早期实现扫描了整个 `bodyText`，使用 `bodyText.includes('草稿')` 判断。
- 页面上始终存在"保存草稿"按钮，按钮文字中包含"草稿"二字，导致误判。

**修复**
- 移除全局 `bodyText.includes('草稿')` 扫描。
- 改为检查实际数据：遍历所有 `.textbox.combo` 容器，确认 `.textbox-value`（hidden 值）是否有非空数值、行内 input/textarea 是否有内容。
- 在 `_prompt_for_existing_records` 中增加"双校验"：即使 `is_detail_page_has_draft` 返回 True，如果 `hourInput=False` 且所有 combo 无选中值，强制视为空记录。

**结论**
> 页面级文字匹配极易被 UI 静态文案干扰。草稿/有记录的判定必须基于**数据状态**（input value、combo hidden-value），而非**界面文案**。

### 坑-2：误删历史任务库数据

**现象**
- 用户要求删除试运行期间的测试数据"测试公共工时填报-集团事务"。
- 脚本执行后删除了 26 条记录，远超预期。

**根因**
- 开发侧误解了删除条件：按 `工作项名称包含"集团事务支撑"` 批量删除，而用户的真实意图是**仅删除 `工作日志 == "测试公共工时填报-集团事务"` 的那一条**。
- 用户指令的颗粒度（工作项 vs 工作日志）没有被显式澄清。

**修复**
- 立即从备份恢复 `task_db.json`。
- 重新执行精确删除：仅删除 `工作日志 == "测试公共工时填报-集团事务"` 且 `申报日期 == 2026-05-19` 的 1 条记录。

**结论**
> 数据删除操作必须**显式确认删除条件**（字段名 + 精确值 + 预期影响条数），不能模糊匹配。涉及生产/半生产数据的删除，应先做备份再执行。

### 坑-3：`KeyError: '日志'`（显式公共任务字典键名不一致）

**现象**
- 执行 `--describe` 后脚本崩溃：`KeyError: '日志'`。
- 堆栈指向 `fill_row_inputs(target_frame, row_idx, item["工时"], item["日志"], is_project=False)`。

**根因**
- `--describe` 解析出的显式公共任务字典使用键 `"工作日志"`（与历史库字段保持一致）。
- 但 `fill_row_inputs` 及后续流程统一期望的键是 `"日志"`（`aggregate_tasks` 输出格式）。
- `FIXED_PUBLIC_TASK` 在修改过程中也一度使用了 `"工作日志"`，导致同一字段存在两种键名。

**修复**
- 统一显式公共任务、`FIXED_PUBLIC_TASK`、手动任务的字典键名为 `"日志"`，与 `aggregate_tasks` 输出格式保持一致。

**结论**
> 数据字典的键名必须在全链路（解析 → 匹配 → 聚合 → 填单）保持一致。不同模块对接时，字段映射关系应显式定义，不能依赖隐式约定。

### 坑-4：公共工作项下拉框为空（未定义工作项映射兜底）

**现象**
- 填报时公共工时最后一行（用户指定的"云服务器续期状态跟踪"）工作项下拉框未选中，留空。
- 控制台输出：`[警告] 工作项 '云服务器续期状态跟踪' 未选中`。

**根因**
- 用户通过 `--describe` 描述的公共工作项"云服务器续期状态跟踪"并非系统预定义的下拉叶子节点。
- EasyUI 的 combotree 下拉数据中不存在该文本，`_select_from_easyui_panel` 查找失败，脚本无兜底逻辑。

**修复**
- 新增 `_resolve_public_workitem(user_wi, db)`：三级映射策略。
  1. 精确匹配历史库中公共工时的 `工作项1/2/3`。
  2. 模糊匹配 `search_text` 中包含用户描述的记录。
  3. 兜底为 `集团事务支撑`（历史库中确认存在的标准叶子节点）。

**结论**
> 用户输入的"工作项名称"不等于系统下拉框中的"标准名称"时，必须有**映射层**做转换，不能直连。兜底策略必须保证系统中有该选项，否则填单必然失败。

### 坑-5：项目日志内容缺失（用户指定内容被历史日志覆盖）

**现象**
- `--describe` 中明确指定了深圳市民政局的日志为"AI自动化测试实践效果查看与沟通"。
- 实际生成的草稿中，民政局项目的日志是历史记录拼接内容，用户指定内容丢失。

**根因**
- `aggregate_tasks` 按 `(申报类型, 项目名称, 工作项叶子)` 分组，组内日志去重拼接。
- `merge_project_rows` 进一步把同一项目下各工作项的日志合并，前缀 `【工作项：...】`。
- 用户通过 `--describe` 指定的日志内容没有在任何阶段被注入，最终在填单阶段也没有覆盖。

**修复**
- 新增 `project_log_map` 字典：`{项目关键词: 用户指定日志内容}`。
- 在 `merge_project_rows` 中增加逻辑：若合并的项目在 `project_log_map` 中存在，直接用用户指定日志，不再拼接历史日志。
- 在 `_run_fill_impl` 最终阶段保留二次保险：再次遍历 items，若项目名称匹配则强制覆盖日志。

**结论**
> 用户明确输入的内容优先级必须高于历史记录推断。全链路中应尽早将"用户指定内容"与"历史推断内容"分离存储，最终合并时以用户指定为准。

### 坑-6：中移信息项目未填入（单一项目垄断 limit）

**现象**
- `--describe` 中提到了"深圳市民政局"和"中移信息2028年充值项目"。
- 生成的草稿中只有民政局项目，中移信息项目完全缺失。

**根因**
- `_match_with_project_coverage` 之前的实现是直接用 `match_tasks(keywords, db, limit=15)` 做整体匹配。
- 深圳民政局在历史库中有 17 条记录，匹配得分高，占满了 `limit=15` 的全部配额。
- 中移信息只有 6 条记录，被挤出前 15 名，导致完全没有被匹配到。

**修复**
- 新增 `_match_with_project_coverage(keywords, db, project_log_map)`：
  1. 对每个 `project_log_map` 中的项目关键词单独调用 `match_tasks(limit=20)`，确保多项目覆盖。
  2. 再用整体 `keywords` 调用 `match_tasks(limit=30)` 作为补充。
  3. 合并去重（虽然 `match_tasks` 返回拷贝，但按引用去重逻辑保留）。

**结论**
> 当用户同时提及多个项目时，全局 Top-N 匹配策略会天然偏向记录数多的项目。多项目场景必须采用"**先分项目保证覆盖，再全局补充**"的两阶段策略。

### 坑-7：同一项目被整体过滤（敏感关键词跨记录污染）

**现象**
- 用户指定的民政局项目和中移信息项目在生成后再次消失。
- 日志显示 `[过滤] 排产非每月上旬(<=10日): 项目成本监控`。

**根因**
- `merge_project_rows` 把同一项目下所有历史记录的日志拼接成一行。
- 该项目下某条历史记录的日志包含"3月排产计划"，合并后整行日志包含"排产"。
- 当天是 22 日（非上旬），`filter_by_date_rules` 检查到"排产"，将整个项目过滤掉。
- 更深层原因：`filter_by_date_rules` 在 `merge_project_rows` **之后**执行，此时已经丢失了逐行区分的粒度。

**修复**
- 调整处理顺序：**先生成 → 逐行过滤日期规则 → 再合并项目行**。
- 包含"排产"的历史记录在合并前就被单独过滤，不会污染整个项目的日志。
- 补充随机后增加二次日期过滤，防止补充记录带敏感词。

**结论**
> 合并操作会损失单记录的粒度信息。任何依赖单记录特征（如日期敏感词）的过滤，必须在**合并之前**完成。

---

### 坑-8：补充记录出现"3月"（月份替换未覆盖补充记录）

**现象**
- 随机补充的中免海南项目日志中仍出现"3月项目复盘"。
- 当前日期为 5 月，按规则应替换为"5月"。

**根因**
- `replace_month_in_logs` 原本放在 `merge_project_rows` 之后、`supplement_with_random` 之前。
- 当匹配结果不足时，`supplement_with_random` 补充的历史记录带有"3月"，但月份替换逻辑已经执行完毕，补充记录未被处理。

**修复**
- 将 `replace_month_in_logs` 移到**所有记录最终确定后**（`supplement_with_random` 之后、`adjust_to_eight` 之前）统一执行。

**结论**
> 任何"后处理"操作（月份替换、敏感词过滤、截断）必须放在**全量数据确定之后**。如果流程中存在"补充/追加"步骤，后处理必须后置到最后一步补充完成后。

---

### 坑-9：固定公共任务重复 3 行（时序依赖导致的重复追加）

**现象**
- 公共工时区域出现 3 行"AI工具引入与推广策划"。
- 预期：每日固定 1 行 2.0H。

**根因**
- 原流程中 `has_fixed` 的判断在 `supplement_with_random` **之前**执行。
- 如果匹配阶段没有"AI工具引入与推广策划"，`has_fixed = False`。
- `supplement_with_random` 补充阶段从历史库中随机抽到 1 条"AI工具引入与推广策划"。
- 后续 `if not has_fixed:` 又追加了一条固定任务。
- 更深层：补充前 `items = [i for i in items if i.get("工作项") not in reserved_names]` 移除了动态项中的同名工作项，但 `has_fixed` 的记忆仍是旧的。

**修复**
- 重构 `_run_fill_impl` 为十步顺序流程：
  1. 生成基础项目 → 2. 过滤+合并 → 3. 手动任务 → 4. 指定公共 → **5. 固定公共（先追加）** → 6. 确保有公共 → **7. 补充随机（后补充）** → 8. 截断 → 9. 月份替换 → 10. 统一调整。
- 固定公共在补充之前追加，补充阶段避开已有工作项叶子，从根本上避免重复。

**结论**
> 当存在"固定追加"和"动态补充"两个来源可能产生同名记录时，**固定追加必须发生在动态补充之前**，或者补充阶段必须显式排除已固定追加的项。状态判断（`has_fixed`）必须与追加动作发生在同一阶段。

### 坑-10：`aggregate_tasks` 内部隐式 adjust 导致后续逻辑混乱

**现象**
- 用户指定项目 + 固定公共 + 补充记录后的总工时计算不符合预期。
- 项目工时忽大忽小，难以预测。

**根因**
- `aggregate_tasks` 内部在最后调用了 `adjust_to_eight(items)`，将匹配到的项目工时强制压缩/放大到 8.0H。
- 后续流程中又加入了固定公共任务 2.0H 和指定公共任务 0.5H，总工时变成 10.5H。
- 最后又调用 `adjust_to_eight(items, reserved_hours=2.5)`，将包含公共工时的所有 items 再次压缩。
- 公共工时的工时也受到了缩放影响（虽然预期是固定不变的）。

**修复**
- 从 `aggregate_tasks` 中移除内部的 `adjust_to_eight` 调用。
- 改为最终阶段统一调整：
  ```python
  dynamic_items = [i for i in items if i.get("申报类型") == "项目工时"]
  public_items = [i for i in items if i.get("申报类型") != "项目工时"]
  reserved_hours = sum(i["工时"] for i in public_items)
  dynamic_items = adjust_to_eight(dynamic_items, reserved_hours=reserved_hours)
  items = dynamic_items + public_items
  ```
- 公共工时保持不变，仅项目工时按 `8.0 - 公共工时总和` 缩放。

**结论**
> 多阶段缩放会导致基数混乱、预期不可控。工时调整应作为**单一后处理步骤**，在所有记录（项目+公共）确定后一次性完成，且明确区分"固定部分"和"可调部分"。

## 四、工程方法改进

1. **数据流单向化**：`aggregate_tasks` 只做聚合，不做缩放；缩放作为最后单一节点执行。
2. **用户输入隔离**：`--describe` 解析出的内容（`project_log_map`、`explicit_public`）应在最终合并阶段注入，不被中间聚合/过滤覆盖。
3. **时序明确化**：固定项 → 用户指定项 → 动态推断项 → 补充项 → 过滤 → 替换 → 缩放。每类数据来源有明确的优先级和插入位置。
4. **兜底显性化**：任何可能匹配失败的字段（工作项、项目）必须有兜底值，且兜底值需预先验证存在于系统中。
5. **删除前置校验**：数据删除前输出"即将删除 N 条记录，条件为..."，用户确认后再执行。

# 集成管理系统浏览器自动化交互复盘

## 一、项目背景

集成管理系统（https://prj.chinasoftinc.com/prj/index.jsp#）基于 **EasyUI + jQuery** 构建，采用经典的 iframe 嵌套日历视图 + 详情页填报结构。本次自动化目标是通过 Playwright CDP 连接本地 Chrome，实现工作日志的自动填报。

整个填单流程涉及：
1. 日历视图选择目标日期
2. 项目工时填报（上半部分）：项目搜索 combo + 工作项 combo + 工时输入 + 日志文本框
3. 公共工时填报（下半部分）：部门 combotree + 工作项 combotree（树形） + 工时输入 + 日志文本框
4. 保存草稿

**核心难点**：EasyUI 组件不是原生 DOM 控件，其状态管理依赖 jQuery 事件链，直接操作 DOM 或 Playwright 标准 API 无法触发内部更新。

---

## 二、踩坑记录与根因分析

### 坑 1：项目搜索框值丢失（F-01）

**现象**：Playwright `locator.fill()` 填入项目名称后，下拉搜索框看似有值，但系统提交时提示"项目未选择"。

**根因**：EasyUI 的 `.textbox.combo` 组件内部维护了一套 jQuery 状态。直接修改 DOM 的 `value` 属性或 Playwright 的 `fill` 只改了显示文本，没有触发 EasyUI 的 `change` 事件和内部隐藏框 `.textbox-value` 的更新。

**修复方案**：
```javascript
// 必须触发完整事件链
jQuery(input).val(name)
input.focus()
input.dispatchEvent(new KeyboardEvent('keydown', {key:'Enter'}))
input.dispatchEvent(new KeyboardEvent('keypress', {key:'Enter'}))
input.dispatchEvent(new KeyboardEvent('keyup', {key:'Enter'}))
input.dispatchEvent(new Event('change', {bubbles:true}))
input.blur()
```

**教训**：对于 EasyUI combo，永远不要用 `element.value = xxx` 或 Playwright `fill()` 直接赋值。

---

### 坑 2：js_verify 误报成功（F-02）

**现象**：脚本扫描页面确认"项目已填入"，但实际填入的是搜索面板里搜索框的值，而非选中的项目。

**根因**：验证逻辑扫描了整个 iframe 的文本内容，范围过大，命中了下拉面板内搜索框的残留文本。

**修复方案**：限定扫描范围到具体的 `.textbox.combo` 容器内：
```javascript
// 错误：扫描整个 document
// 正确：仅扫描当前 combo 容器
const container = el.closest('.textbox.combo')
const text = container.querySelector('.textbox-text')?.value
const value = container.querySelector('.textbox-value')?.value
```

**教训**：DOM 验证必须限定到组件容器级别，不能全局搜索。

---

### 坑 3：工作项死循环/递归溢出（F-03）

**现象**：脚本运行到工作项选择时卡死，Playwright 报调用栈溢出。

**根因**：在树形下拉（`.combotree`）中，Playwright 的 `locator.click()` 定位到了祖先容器而非目标节点。代码逻辑误判为"点击了非叶子节点 → 需要展开 → 递归展开 → 再次点击同一祖先容器"，形成无限递归。

**修复方案**：彻底弃用 Playwright `locator.click()`，全部改用 JS 直接点击：
```javascript
// 错误：await locator.click()
// 正确：await locator.evaluate("el => el.click()")
```

**教训**：在 EasyUI 树形/复杂组件中，`locator.click()` 的行为不可预测。JS evaluate 是更可靠的选择。

---

### 坑 4：工作项下拉内容为空 `[]`（panel 范围过广）

**现象**：打开工作项下拉后，面板内只显示 `[]`，没有任何选项。

**根因**：`close_all_easyui_panels` 清理函数中使用了 `.panel:visible` 来隐藏所有可见面板。`.panel` 在 EasyUI 中是一个极其宽泛的类，覆盖了页面上的各种结构容器（包括下拉面板自身的渲染容器）。误隐藏后，后续下拉面板的内容无法正确渲染。

**修复方案**：
```javascript
// 错误：jQuery('.panel:visible').hide()
// 正确：仅清理 combo 面板和遮罩层
jQuery('.combo-panel:visible').hide()
jQuery('.window-mask').hide()
```

**教训**：`.panel` 是 EasyUI 的通用结构类，范围极大，操作时必须使用更精确的选择器（如 `.combo-panel`、`.panel-htop`）。

---

### 坑 5：工作项面板检测不到

**现象**：下拉展开后，脚本遍历面板内容时找不到任何选项节点。

**根因**：面板选择器只写了 `.panel-htop, .combo-panel`，但实际渲染的面板节点使用了 `.panel` 类。

**修复方案**：面板选择器统一扩展为 `.panel-htop, .combo-panel, .panel`。

**教训**：EasyUI 的面板类名不唯一，查询时应该使用"或"关系覆盖多种可能。

---

### 坑 6：工作项下拉框点错区域（面积误判）

**现象**：脚本点击了公共工时区域的第1行工作项，但打开的是整个公共工时列表的大下拉（168项），导致后续选择逻辑完全错乱。

**根因**：`_click_combo_arrow_by_placeholder` 使用 `section_hint`（如"公共工时填报"）来定位填报区域。代码原逻辑是取第一个匹配该文本的 `div`，但这个 div 往往是标题小区域，面积很小；真正的大容器是后面面积更大的 div。

**修复方案**：
1. 遍历所有匹配 `section_hint` 的 div，取 `offsetWidth * offsetHeight` 面积最大者作为目标区域
2. 增加 `index` 参数，精确定位区域内第 N 个输入框（按行索引）

**教训**：通过文本定位区域时，必须考虑页面上可能存在多个匹配节点，要用面积或层级来筛选真正的容器。

---

### 坑 7：最后一行工作项未填入（JS click 假成功）

**现象**：脚本日志显示"成功选择工作项"，但系统页面上最后一行的工作项字段为空。前几行正常。

**根因**：`item.click()` 对 EasyUI datagrid-cell 元素不能触发内部状态更新。EasyUI 的单元格组件依赖完整的鼠标事件序列（`mousedown` → `mouseup` → `click`）来更新表单值，简单的 JS `click()` 事件不完整。

**修复方案**：
```javascript
// 错误：item.click()
// 正确：完整鼠标事件序列
item.scrollIntoView({block:'nearest'})
item.dispatchEvent(new MouseEvent('mousedown', {bubbles:true}))
item.dispatchEvent(new MouseEvent('mouseup', {bubbles:true}))
item.dispatchEvent(new MouseEvent('click', {bubbles:true}))
```

**教训**：对于 EasyUI datagrid/combotree 的叶子节点点击，必须模拟完整鼠标事件序列，不能简化为单一的 `click()`。

---

### 坑 8：保存草稿按钮 disabled 超时

**现象**：所有字段填完后，Playwright `get_by_text("保存草稿").click()` 超时失败，报错"元素不可交互"。

**根因**：EasyUI 在表单验证过程中会临时将按钮设为 `disabled`（如必填项未通过校验时）。Playwright 的标准 click 无法点击 disabled 元素。

**修复方案**：增加 JS click 兜底：
```python
try:
    target_frame.get_by_text("保存草稿").click()
except Exception:
    target_frame.evaluate("""
        () => { var btn = document.getElementById('btnSaveDraft'); if (btn) btn.click(); }
    """)
```

**教训**：EasyUI 的按钮状态会动态变化，Playwright click 对 disabled 元素严格失败，必须准备 JS 兜底方案。

---

### 坑 9：填错日期（页面状态残留）

**现象**：传入 `--date 2026-05-22`，但脚本把内容填到了 5 月 20 日的详情页里。

**根因**：`ensure_on_calendar` 原逻辑仅检查 URL 是否包含目标域名。如果浏览器当前停留在某日的详情页（如 5 月 20 日），URL 仍然包含目标域名，脚本误判为"已在日历页"。后续 `find_and_click_date` 在详情页中找不到日历元素，但脚本没有正确终止，导致在错误的页面上继续执行填单逻辑。

**修复方案**：`ensure_on_calendar` 改为无条件强制导航到日历首页：
```python
def ensure_on_calendar(page):
    page.goto(BASE_URL)
    page.wait_for_timeout(3000)
```

**教训**：永远不要假设浏览器停留在期望的页面。每次执行填单前，强制导航到流程起点。

---

### 坑 10：未来日期无拦截

**现象**：传入未来日期（如后天），系统日历上该日期不可点击，脚本点击后页面无反应，但脚本继续执行，导致在日历页上尝试填单而报错。

**根因**：`find_and_click_date` 点击日期后没有验证是否真正进入了详情页。

**修复方案**：
1. 点击后等待 2 秒，检查页面是否出现了详情页特征元素（`#btnSaveDraft` 或 `input[type='number']`）
2. 在 `_run_fill_impl` 开头增加前置校验：若目标日期大于今天，直接终止，不连接浏览器

**教训**：任何"点击 → 页面跳转"操作后，都必须用 DOM 元素存在性验证跳转结果，不能假设跳转一定成功。

## 三、系统技术架构

### 3.1 前端框架

| 层级 | 技术 | 说明 |
|------|------|------|
| UI 框架 | EasyUI 1.x（jQuery 插件） | 所有表单组件均为 jQuery 插件封装，非原生 DOM |
| 基础库 | jQuery 1.x | EasyUI 依赖 jQuery 的事件系统和选择器 |
| 页面结构 | iframe 嵌套 | 日历和填报表格位于 iframe 中，主页面仅导航栏 |
| 弹窗/面板 | EasyUI Panel/Window | `.panel`、`.panel-htop`、`.window-mask` |

### 3.2 关键组件结构

#### 3.2.1 标准下拉框（`.textbox.combo`）

用于：项目搜索、项目工作项选择

```html
<div class="textbox combo">
  <input class="textbox-text" type="text">      <!-- 显示文本 -->
  <input class="textbox-value" type="hidden">    <!-- 实际提交值 -->
  <span class="combo-arrow"></span>              <!-- 下拉箭头 -->
</div>
<div class="combo-panel panel">                  <!-- 下拉面板 -->
  <!-- 选项列表 -->
</div>
```

**状态更新路径**：`.textbox-text` 的值变化 → jQuery 事件链 → `.textbox-value` 更新 → EasyUI 内部状态更新

#### 3.2.2 树形下拉框（`.combotree`）

用于：公共工时工作项选择（多级树形菜单）

```html
<div class="textbox combo combotree">
  <input class="textbox-text">
  <input class="textbox-value">
  <span class="combo-arrow"></span>
</div>
<div class="combo-panel panel">
  <div class="tree">                              <!-- 树形结构 -->
    <div class="tree-node">                       <!-- 非叶子节点（文件夹） -->
      <span class="tree-indent"></span>
      <span class="tree-hit tree-expanded"></span>
      <span class="tree-icon tree-folder"></span>
      <span class="tree-title">交付管理类</span>
    </div>
    <div class="tree-node">                       <!-- 叶子节点（可选值） -->
      <span class="tree-indent"></span>
      <span class="tree-indent"></span>
      <span class="tree-hit tree-collapsed"></span>
      <span class="tree-icon tree-file"></span>
      <span class="tree-title">AI工具引入与推广策划</span>
    </div>
  </div>
</div>
```

**关键区分**：叶子节点的 `.tree-icon` 是 `tree-file`，非叶子节点是 `tree-folder`。只有叶子节点才能被选中。

#### 3.2.3 日历视图

```html
<table>
  <tr>
    <td>
      <div class="calendar-day">20</div>
      <div class="calendar-text">申报8h</div>       <!-- 已有填报记录 -->
    </td>
  </tr>
</table>
```

**状态识别**：单元格内包含"申报"、"审批"等字样，表示该日期已有记录。

#### 3.2.4 填报详情页

```html

  <span>项目工时填报</span>
  <button>+ 增加行</button>

    <tr>
```

## 四、组件交互速查表

### 4.1 通用原则

| 原则 | 说明 |
|------|------|
| **禁用 Playwright click** | 全部使用 `locator.evaluate("el => el.click()")` |
| **禁用直接 DOM 赋值** | EasyUI 组件必须用 jQuery 事件链更新 |
| **操作后验证** | 每次点击/选择后，用 DOM 元素存在性验证结果 |
| **强制导航起点** | 每次执行前 `page.goto(BASE_URL)`，不假设当前页面 |
| **精确限定范围** | 验证和查询时必须限定到组件容器，禁止全局扫描 |

### 4.2 按组件类型的正确操作方式

#### 标准 Combo（项目搜索、工作项选择）

| 操作 | 错误做法 | 正确做法 |
|------|----------|----------|
| 填充值 | `input.value = xxx` | jQuery.val() + 完整事件链 |
| 展开面板 | `arrow.click()` | `jQuery(combo).combo('showPanel')` 或 JS 点击 arrow |
| 选择选项 | Playwright click 选项 | JS 遍历 `.combo-panel` 内节点，找到匹配文本后模拟完整鼠标事件 |
| 验证结果 | 全局扫描文本 | 限定到 `.textbox.combo` 容器内扫描 `.textbox-text` / `.textbox-value` |

#### Tree Combo（公共工时工作项）

| 操作 | 错误做法 | 正确做法 |
|------|----------|----------|
| 选择叶子 | 直接点击 `.tree-title` | 先判断是否叶子节点（`tree-file` 图标），再模拟完整鼠标事件序列 |
| 展开父节点 | 递归无限展开 | 只展开非叶子节点（`tree-folder`），叶子节点直接点击 |

#### 日历日期

| 操作 | 错误做法 | 正确做法 |
|------|----------|----------|
| 点击日期 | 找到数字就点击 | 点击后验证是否进入详情页（检查 `#btnSaveDraft` 或 `input[type='number']`） |
| 识别已填报 | 扫描数字 | 扫描单元格内是否包含"申报"、"审批"字样 |

#### 按钮

| 操作 | 错误做法 | 正确做法 |
|------|----------|----------|
| 点击保存 | 仅 Playwright click | Playwright click 为主，JS `document.getElementById('btnSaveDraft').click()` 兜底 |

## 五、调试方法论（已验证有效）

### 5.1 先诊断后动手

遇到页面交互问题，优先编写诊断脚本（JS 查询 DOM 结构），而非盲目修改 selector。

**诊断模板**：
```javascript
() => {
  // 1. 确认元素存在性
  const el = document.querySelector('你的选择器')
  if (!el) return { exists: false }

  // 2. 确认元素位置和尺寸
  const rect = el.getBoundingClientRect()

  // 3. 确认元素可见性
  const style = window.getComputedStyle(el)

  // 4. 确认父级结构
  const parent = el.parentElement?.className

  // 5. 确认同类元素数量
  const siblings = document.querySelectorAll('相同选择器').length

  return { exists: true, rect, display: style.display, parent, siblings }
}
```

### 5.2 增量调试（单行先行）

新增功能（如增加行、选择工作项）先测单行，验证通过后再扩展多行。原因：多行同时失效时，无法判断是第几行的定位出了问题，还是整体逻辑有问题。

**执行顺序**：
1. 先填第 1 行项目工时 → 截图验证 → 通过
2. 再填第 1 行公共工时 → 截图验证 → 通过
3. 最后扩展到多行

## 六、下次扩展功能时的检查清单

在集成管理系统上实现任何新自动化功能前，按此清单确认：

- [ ] 新页面是否使用了 iframe？需要 `page.frames` 遍历定位
- [ ] 新表单是否使用了 EasyUI 组件？需要 jQuery 事件链而非直接 DOM 操作
- [ ] 下拉选择是标准 combo 还是树形 combotree？树形需要判断叶子节点
- [ ] 按钮是否有动态 disabled 状态？需要 JS click 兜底
- [ ] 操作后是否有页面跳转或异步加载？需要 DOM 元素存在性验证
- [ ] 选择器是否足够精确？避免使用 `.panel` 等宽泛类名
- [ ] 是否从已知的流程起点开始？强制导航，不依赖当前页面状态

## 八、总结

集成管理系统的自动化核心难点不在于业务逻辑，而在于 **EasyUI 组件的事件驱动模型与 Playwright 标准 API 之间的语义鸿沟**。Playwright 设计用于操作标准 DOM，而 EasyUI 在 DOM 之上构建了完整的状态管理层（jQuery 插件体系），直接操作 DOM 不会触发内部状态更新。

**最高效的调试路径**：
1. 遇到交互失败 → 先用浏览器 DevTools 手动执行相同操作，观察 DOM 变化和事件触发
2. 编写诊断脚本复刻手动操作的 DOM 变化
3. 将诊断脚本固化到生产代码中
4. 永远保留 JS evaluate 作为 Playwright API 的兜底方案

这份复盘中的坑、架构图、速查表和代码片段，应在下次扩展功能时直接引用，避免重复踩坑。
